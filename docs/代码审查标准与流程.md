# PaperForge 代码审查标准与流程（Code Review Standard & Process）

> 版本：v1.0 ｜ 制定：Code Review Expert ｜ 日期：2026-07-16
> 配套文档：`docs/团队技术提升与代码质量把控方案.md`（提升路线图，本文的执行依据来源）
> 适用：所有进入 `main` / `develop` 的 Pull Request

---

## 0. 本文定位

本文是团队代码审查的**权威执行手册**。已有方案文档讲"为什么做、分几步走"，本文讲"**具体怎么审、按什么标准、谁在何时卡**"。

三者关系：

| 文档 | 角色 | 读者 |
| :--- | :--- | :--- |
| `团队技术提升与代码质量把控方案.md` | 提升路线图（分阶段、为什么） | 技术负责人 / 新人 onboarding |
| **本文 `代码审查标准与流程.md`** | **审查执行手册（审什么、怎么审）** | **每位提交者与 Reviewer** |
| `.pre-commit-config.yaml` + `ci.yml` | 自动化门禁（工具拦截） | 机器 + 提交者 |

核心思路不变：**不靠自觉靠机制**——工具门禁挡低级错误，CR 标准把经验固化成可执行清单，本文把两者串成一条可落地的流水线。

---

## 1. 审查原则

1. **门禁优先**：能由 `pre-commit` / `ci.yml` 自动拦截的，绝不靠人工 review 兜底。人工只审工具看不出、但影响正确性 / 安全 / 可维护性的东西。
2. **风险分级**：问题按 🔴 / 🟡 / 💭 三级定处置规则（见 §4）。🔴 必须清零才能合并。
3. **教学优先**：每条评论都讲 **Why**，不只说改什么。最好的 review 让作者下次自己不犯。
4. **建议不命令**：用"考虑 / 建议"，不命令"必须改成 X"。但 🔴 是硬性门槛，无商量余地。
5. **作者负责制**：提交者对自己的代码质量负首要责任；reviewer 是兜底与把关，不是代写。

---

## 2. 角色与职责

| 角色 | 职责 | 谁担任 |
| :--- | :--- | :--- |
| **Author（作者）** | 提交前跑通自检与门禁；PR 描述写清"改了什么、为什么、怎么测"；先修 AI/reviewer 标出的 🔴 | 提交者本人 |
| **AI Reviewer（Code Review Expert）** | 第一道自动审查：对 diff 产出分级评论，先把 🔴 揪出来 | 本助手（提交 PR 后调用） |
| **Reviewer（人类）** | 按本文 Checklist 逐项确认；对 🔴 裁决是否真阻塞；给 approval | 团队轮值（见 §7 轮值制） |
| **资深开发者（守门人）** | 关键路径（DB 迁移、鉴权、异步核心、对外 API 契约）必看；裁决争议 | 技术负责人 |

> 小团队现实：若当前只有你和 AI，则流程为 **Author 自检 → AI 审查先清 🔴 → 你作为人类终审合并**。轮值制在你扩队后启用。

## 3. 审查流程（端到端）

```
提交前 ──▶ 开 PR ──▶ 自动门禁(CI) ──▶ AI 审查(清🔴) ──▶ 人类 Review ──▶ 合并门禁 ──▶ 合并
  │            │            │                │                │              │
 pre-commit   PR 模板    ruff/mypy/pytest  分级评论         Checklist     1 approval
 本地 pytest   门禁全绿   前端 lint/format   作者先修🔴       ≥1 approval   覆盖率不降
```

### 阶段 0 · 作者自检（提交前）
**目标：让 PR 一开出来就接近可合并状态。**

- [ ] `pre-commit run --all-files` 全绿（ruff、ruff-format、debug-statements、check-merge-conflict、no-inline-workers 自动拦截）
- [ ] 本地跑关键测试：`pytest -m critical -q`（红绿灯门禁，先确认核心路径没坏）
- [ ] 对照本文 §5 对应域的清单自查一遍
- [ ] 前端改动额外跑：`cd web && npm run format`（**必做**，否则 `format:check` 门禁会红——这是复发过的坑，根因是有人提交前端没跑 prettier）
- [ ] 自测：手动走一遍改动涉及的功能路径

### 阶段 1 · 开 PR + 自动门禁
- 用 PR 模板（见 §8 / `.github/PULL_REQUEST_TEMPLATE.md`）填描述。
- **门禁不全绿，不允许进入 review**。CI 会跑：
  - 后端：`ruff check mock_api` → `mypy mock_api` → `pytest --cov-fail-under=70` → `pytest -m critical`
  - 前端：`npm run lint` → `npm run format:check` → `npm run build` → `npx vitest run`
- 任一门禁红，Author 先修，不占用 reviewer 时间。

### 阶段 2 · AI 审查（第一道自动审查）
- 提交 PR 后，把 diff 或 PR 编号交给 **Code Review Expert**（即本助手），产出分级评论。
- **作者先修完所有 🔴**，再请求人类 review——把资深 human reviewer 的时间留给工具看不出的设计 / 安全判断。
- 调用方式（在本助手对话中）："审查 PR #NN 的 diff" 或粘贴改动片段。

### 阶段 3 · 人类 Reviewer 审查
- 至少 **1 名** Reviewer approval；**关键路径**（DB 迁移、鉴权、`routers/`、`crud/` 包、对外 API）需 **2 名**（含资深开发者）。
- 按本文 §5 分域清单逐项确认，评论用 §6 格式。
- 🔴 必须逐一关闭；🟡 由 Author 与 Reviewer 协商（可记 issue 后续跟）；💭 口头或备注即可。
- 争议由资深开发者裁决。

### 阶段 4 · 合并门禁
合并前硬性条件（任一不满足则驳回）：
- [ ] 所有 🔴 已关闭（有合理说明或 issue 跟踪）
- [ ] 至少 1 approval（关键路径 2）
- [ ] 覆盖率门禁不降（当前 `--cov-fail-under=70`，阶段 3 提 80）
- [ ] 无 merge conflict、无遗留 `debug-statements`
- [ ] 推荐 **squash merge**，保持 `main` 历史干净

## 4. 问题分级标准（处置规则）

| 级别 | 含义 | 典型例子 | 处置 |
| :--- | :--- | :--- | :--- |
| 🔴 **Blocker** | 合并前必须修，否则有安全/数据/正确性风险 | SQL 注入、路径穿越、裸 `except`、破坏对外 API 契约、迁移丢数据、关键路径无错误处理 | **零容忍，合并前清零** |
| 🟡 **Suggestion** | 应该修，影响可维护性/性能/健壮性 | 缺输入校验、命名歧义、缺测试、N+1 查询、重复代码未抽、异步里调阻塞 IO | 本 PR 修或开 issue 跟踪，reviewer 把关 |
| 💭 **Nit** | 锦上添花，不影响运行 | 注释缺失、小命名、风格细节（工具已管的别人工挑） | 建议即可，不阻塞 |

> 工具已管的不算人工 review 项：ruff/black/isort 管的格式、pre-commit 管的基础卫生，人工不必重复挑。

## 5. 分域审查清单（核心）

> 这是本文重点。按改动落点选对应域逐项确认。

### 5.1 后端 · Python / FastAPI（`mock_api/`）

**分层纪律（最重要）**
- [ ] `routers/` 只做：参数解析（Pydantic）、调用 service/crud、组装响应。**不放业务与 DB 查询**。
- [ ] 业务逻辑进 `crud/` 包（`analysis/embeddings/notes/papers/search/stats/writing`）或 `services/`，不要回潮到 `main.py`。
- [ ] 新论文表操作走 `crud/papers.py` 等；ORM 导入用 `from .models import Paper as PaperORM`（**别写 `PaperORM` 当类名**，运行时 ImportError，py_compile 查不出）。

**错误处理**
- [ ] 禁止裸 `except:`；`except Exception` 必须 `logger.exception(...)`（保留上下文与因果链，别只 `pass`）。
- [ ] `except` 内 `raise` 新异常带 `from e`（对应存量 B904 短板）。
- [ ] 对外 API 返回**结构化错误**（HTTP 状态码 + 错误体），不把内部堆栈抛给前端。

**输入校验 / 安全**
- [ ] 所有外部输入走 Pydantic 模型校验（类型、范围、长度）。
- [ ] 文件路径 / 代理类接口做**路径穿越 + SSRF** 校验（参考既有 `pdf_proxy_service.py` 做法，别退化）。
- [ ] 密钥 / Token 走环境变量（`.env` / `settings`），**绝不硬编码**。
- [ ] `admin` 端点受 `ENV=development` 保护，别在生产暴露。

**数据库 / SQLAlchemy 2.0**
- [ ] 用 2.0 风格：`Mapped[...]` + `mapped_column(...)`，不用旧 `Column(...)` 裸写法。
- [ ] **无 N+1**：关联用 `joinedload` / `selectinload`；批量用 `bulk_*` / `executemany`。
- [ ] 不在循环里逐条 `commit()`；长事务注意锁与超时。

**异步 / 任务**
- [ ] `async def` 路由里**不调阻塞 IO**（CPU 重活、同步库）；重任务走 `tasks.py` 的 `TaskManager`（SSE 模式），**别新建 Celery / RQ / WebSocket**。
- [ ] 内存缓存 / 幂等走内存方案（如 `export_tasks.py` 的 dict），**Redis 刻意不引入**，别擅自加。

**配置 / 日志 / 类型**
- [ ] 配置走 `settings.get_settings()` 单一事实源；**不新增 `config.py` 这类 shim**。
- [ ] 用 `logging.getLogger(__name__)`，禁止 `print()` 调试残留。
- [ ] 新代码函数签名带类型注解；核心模块逐步 `mypy` 收敛。

### 5.2 前端 · React / TypeScript（`web/src/`）

**分层与接口**
- [ ] 分层清晰：`pages/`（页面）、`components/`（组件）、`api/`（接口封装）、`store/`（状态）。新逻辑不堆进单文件。
- [ ] 接口地址**必须经 `VITE_API_BASE` 拼接**，不硬编码 `/api/...`；图片 / 资源用 `resolveAssetUrl()` 处理，否则自定义 API 基址部署时会指向错误源站（这是修过的坑）。

**错误处理 / 健壮性**
- [ ] **所有请求包 `try/catch/finally`**，失败时收起 spinner、显示错误提示——别让 spinner 挂死、别把"无命中"误报成"向量不可用"（修过的坑）。
- [ ] 不滥用 `dangerouslySetInnerHTML`；确需渲染 HTML 须先做净化，防 XSS。

**类型 / 性能 / 格式**
- [ ] TS 严格模式；组件 props 用 `interface` / `type` 声明。
- [ ] 长列表虚拟化 / `memo`；大响应不一次性 load 进内存。
- [ ] 提交前 `npm run format`（prettier）必跑，否则 `format:check` 门禁红。

### 5.3 数据库迁移 · 单一事实源（`_migrate_schema`）
- [ ] schema 变更**只走一处**：改 `models.py` 后必须同步 `mock_api/database.py::_migrate_schema()`（ALTER TABLE ADD COLUMN 补齐列，幂等），二者由 CI 断言（`tests/test_database_migration.py`）守卫一致。
- [ ] **Alembic 已退役（2026-07-19 F3）**：禁止再引入 `alembic/` 或运行 `alembic upgrade head`，避免双轨漂移建出缺列残缺库。
- [ ] 不擅自删列 / 改列类型导致数据丢失；破坏性变更（`depth_scores` 重建等）先经 forensic 快照兜底。
- [ ] 新增 ORM 模型必须确保 `_migrate_schema` 能追平（legacy 库升级路径由测试覆盖）。

### 5.4 测试（`tests/`，`web/` 前端测试）
- [ ] 新功能配 `critical` 或 `contract` 标记测试；**bug 修复必须配回归测试**（防止复发）。
- [ ] 不降低覆盖率门禁（`--cov-fail-under=70`，阶段 3 提 80）。
- [ ] 测试可独立运行（`conftest.py` 已做防护）；不依赖外部网络 / 真实 LLM（用 mock/fixture）。

### 5.5 安全专项（跨域必查）
- [ ] **注入**：SQL（用参数化，禁字符串拼接）、命令注入、模板注入。
- [ ] **XSS**：前端渲染外部内容须净化。
- [ ] **路径穿越 / SSRF**：文件、代理类入口校验。
- [ ] **鉴权 / 授权**：`admin` 端点门禁；不泄露内部细节给未授权方。
- [ ] **密钥**：不硬编码，走 env。

## 6. 评论写法规范

每条评论用统一格式，便于作者快速定位与执行：

```
🔴 **安全：SQL 注入风险**
文件:行号：用户输入直接拼进查询。

Why：攻击者可注入 `'; DROP TABLE ... --`，导致数据丢失。

Suggestion：
- 改用参数化：`db.execute(select(X).where(X.name == :name), {"name": name})`
```

规则：
- 必须带级别标记 + 具体文件:行号（别只说"这里有安全问题"）。
- 必须讲 **Why**（影响 / 根因），不只给结论。
- 用"建议 / 考虑"，🔴 之外不命令。
- **夸好代码**：发现清晰的分层、巧妙的处理，明确点名表扬——正向反馈让标准被认同。
- 对事不对人：说"这段逻辑在 X 情况下会…"，不说"你又写错了"。

## 7. 轮值与持续改进

**Reviewer 轮值制**（扩队后启用）
- 每人按周轮值做 Reviewer；资深开发者在阶段 1–2 每 PR 必看，逐步把把关能力传给团队。
- 关键路径 PR 指定资深开发者二审。

**度量（月度回顾）**
- 跟踪：🔴 关闭率、平均 review 时长、CI 门禁红次数、重复出现的问题类型。
- 把**反复出现**的问题固化进本文 §5 清单（例如历史上 prettier 复发、spinner 挂死、图片地址硬编码，都曾是"修一次忘一次"的坑，现已写入清单）。

**知识沉淀**
- 每次踩坑更新 `RUNBOOK.md` 与本文对应章节；新约定进 `MEMORY.md`（项目记忆）。
- 本文随项目演进修订，版本号 + 日期随改随升。

## 8. PR 模板（已建 `.github/PULL_REQUEST_TEMPLATE.md`）

开 PR 时自动带出，作者填：
- **改动摘要**：做了什么、为什么。
- **影响域**：后端 / 前端 / 迁移 / 测试（多选）。
- **自测**：本地跑了哪些测试 / 手动验证了什么。
- **门禁**：pre-commit 与 CI 是否全绿（贴链接）。
- **需重点 review 的点**：主动标出你拿不准的设计 / 安全判断。

## 9. 门禁命令速查

| 场景 | 命令 |
| :--- | :--- |
| 提交前全量自检 | `pre-commit run --all-files` |
| 后端 lint | `ruff check mock_api` |
| 后端类型 | `mypy mock_api` |
| 后端测试 + 覆盖率 | `pytest --cov=mock_api --cov-fail-under=70` |
| 红绿灯（核心路径） | `pytest -m critical -q` |
| 前端 lint | `cd web && npm run lint` |
| 前端格式检查 | `cd web && npm run format:check` |
| 前端格式化（提交前必跑） | `cd web && npm run format` |
| 前端测试 | `cd web && npx vitest run` |

> Windows 沙箱 pytest 带 `--cov` 因回收站不可用会崩，本地验收用 `pytest -o addopts=""`。
