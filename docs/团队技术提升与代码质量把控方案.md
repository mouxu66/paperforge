> 版本：v1.0 ｜ 制定：资深开发工程师 ｜ 日期：2026-07-09
> 目标：以可落地的机制补齐工程化短板，把"代码质量把控"从口头约定变成「工具门禁 + 团队习惯」。

## 一、现状诊断（基于代码库实测）

项目已有不错的基础。以下为客观事实，非主观感受。

### 优势（请保持）
- 后端分层雏形清晰：`routers/`（只做路由）、`services/`、`llm/`（base/factory/errors/provider 拆分）、`admin/`。
- 配置管理规范：`settings.py` 用 pydantic-settings 做单一事实来源，fail-fast 校验，单例 `get_settings()`。
- CI 已建：`.github/workflows/ci.yml` 多版本矩阵 + 覆盖率门禁 `--cov-fail-under=70`，测试标记（critical/contract/integration/e2e）分组运行。
- 测试基础尚可：约 350 个 `test_*` 函数、38 个测试类、`conftest.py` 有防护逻辑（README 记为 262 个单元测试，数量随版本增长）。

### 短板（按严重度排序，是本次提升重点）
- **P0 巨文件（god-file）**：`mock_api/main.py` 约 3699 行、`mock_api/crud.py` 约 2955 行。所有领域 handler 堆在一个文件，分层被弱化，新人不敢改、老手怕改坏。
- **P1 重复代码**：深度评估存在 `depth_eval` / `depth_eval_v4` / `_reflection` / `depth_pipeline` 四套近似模块；`_clamp_float`、`_clamp_list` 在多处重复实现（已 `comm` 确认）。这是 copy-paste 演化的典型信号。
- **P1 工程化缺失**：无 `ruff`/`flake8`、无 `mypy`、无 `black`/`isort`、无 `pre-commit`、无 `pyproject.toml`。静态检查、类型校验、格式化、提交钩子全缺，代码风格靠自觉。
- **P2 日志不规范**：56 处 `print()` 绕过日志系统；全仓无集中日志配置（`basicConfig`/`dictConfig` 未定义），级别/格式/输出未统一。
- **P2 错误处理偏宽泛**：184 处 `except Exception`，多数未记录上下文，排障时只能盲猜。
- **P2 配置 shim 脆弱**：`config.py` 仍是 `settings.py` 的兼容层，顶层 `= get_settings()` 存在导入顺序脆弱性与循环依赖风险。

## 三、代码质量把控机制（已落地，如何使用）

### 1. 工具链配置 `pyproject.toml`
统一了 ruff（lint + format）、black、isort、mypy 的规则，团队不再各用各的。关键规则：
- 行宽 100；ruff 开启 E/F/I/B/C4/UP/SIM/W/ASYNC 等规则集。
- 对 `main.py`/`crud.py` 暂时放宽复杂度（C901）与导入顺序（E402），避免存量报错淹没新规则——这是「渐进式质量门禁」策略。

### 2. 提交前门禁 `.pre-commit-config.yaml`
任何人提交前自动执行：
- 基础检查（trailing-whitespace、end-of-file-fixer、check-yaml、check-added-large-files、check-merge-conflict、debug-statements）
- `ruff` 自动修复 + `ruff-format`
- `mypy`（仅 `mock_api/`，类型渐进）

### 3. 本地使用步骤（一次配置，长期受益）
```bash
# 安装 pre-commit（建议用项目虚拟环境）
pip install pre-commit
pre-commit install

# 之后每次 git commit 自动触发；也可手动全量检查：
pre-commit run --all-files
```

### 4. CI 加固建议（阶段 3）
在 `ci.yml` 中新增 job：
```yaml
quality:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-python@v5
      with: { python-version: "3.11" }
    - run: pip install ruff mypy
    - run: ruff check mock_api
    - run: mypy mock_api
```

## 四、Code Review Checklist（团队照此把关）

提交 PR 时，reviewer 逐项确认。资深开发者重点守前两栏。

### 设计 & 可读性
- [ ] 单一职责：函数 ≤ 50 行、文件 ≤ 400 行（存量 god-file 例外，但新代码必须遵守）
- [ ] 无重复：发现相似逻辑先抽公共函数，不复制粘贴
- [ ] 命名清晰语义化，不滥用缩写；变量名能表达意图

### 健壮性 & 错误处理
- [ ] 禁止裸 `except:`；`except Exception` 必须 `logger.exception(...)` 记录上下文
- [ ] 对外 API 返回结构化错误，不把内部堆栈直接抛给前端
- [ ] 不信任任何用户输入：路径穿越、SSRF、注入逐一校验（参考 `pdf_proxy_service.py` 既有做法）

### 日志 & 可观测
- [ ] 使用 `logging.getLogger(__name__)`，**禁止 `print()` 调试残留**
- [ ] 关键路径（导入、问答、导出）有结构化日志，便于排障

### 类型 & 测试
- [ ] 新代码函数签名带类型注解
- [ ] 新功能配 `critical`/`contract` 测试；bug 修复配回归测试
- [ ] 不降低现有覆盖率门禁（70%，阶段 3 提 80%）

### 性能 & 安全
- [ ] 无 N+1 查询；批量操作用 bulk
- [ ] 大文件/大响应走流式，不一次性 load 进内存
- [ ] 密钥/Token 走环境变量，不硬编码

## 附录：存量问题基线（ruff 0.15.20，2026-07-09）

对 `mock_api/` 全量扫描，共 **399** 个问题，其中 **299** 个可由 `ruff --fix` 自动修复。

| 规则 | 数量 | 含义 | 自动修复 |
| :--- | :--- | :--- | :--- |
| UP045 | 172 | 类型注解未用 PEP 604（`Optional[X]` → `X \| None`） | 是 |
| I001 | 44 | 导入未排序 | 是 |
| F401 | 37 | 未使用的 import | 是 |
| B904 | 33 | except 内 raise 未带 `from`（丢失因果链） | 否 |
| SIM105 | 21 | 可抑制的异常分支 | 否 |
| UP035 | 15 | 废弃的 import | 是 |
| F841 | 12 | 未使用的变量 | 否 |
| UP006 | 10 | 注解未用 PEP 585（`List` → `list`） | 是 |
| UP037 | 8 | 多余引号注解 | 是 |
| 其他（C416/C420/B033/SIM102/W293 等） | 47 | 各类可优化项 | 部分 |

**解读（资深视角）：**
- 前三类（UP045/I001/F401，共 253 个，占 63%）属于「纯风格 / 现代化」问题，**一键 `ruff --fix` 即可消除**，应作为阶段 1 第一批清理，立刻让代码整洁。
- B904（33 个）与错误处理强相关：在 `except` 内重新 raise 却丢了原始因果链，排障时会丢失根因——这正是「错误处理偏宽泛」短板的量化证据，需在重构时逐个补 `from e`。
- 剩余约 100 个需要人工判断（变量未用、可简化分支等），适合作为新人练手 PR，由 reviewer 把关。

**建议的第一刀（低风险、高收益）：**
```bash
# 先提交当前状态作为基线，再批量自动修复风格问题
git add -A && git commit -m "chore: baseline before lint cleanup"
ruff check mock_api --fix   # 自动修复 299 个
ruff format mock_api        # 统一格式
git add -A && git commit -m "style: ruff auto-fix (UP045/I001/F401/UP006...)"
```

本方案的核心思路是「不靠自觉靠机制」：工具链 + 提交门禁把低级错误挡在提交前，CR Checklist 把资深经验固化成团队可执行的标准，重构实战把提升落到代码里。
